# Model observation and action evidence

## Claim

The configured MTF reasoning policy uses shared historical timeframe streams
and a 109-element setup choice/mask. The conditioned variant additionally
uses the selected setup ID's learned embedding for execution-head conditioning.
Neither policy represents 108 separate return regressions or, by this
architecture alone, a proposed-price-specific fill/return model. Supported
candidate episode starts range from 3 to 24,413; these are context-state starts,
not independent trades.

## Recorded run shapes and trace availability

[`run_artifact_shape_inventory.json`](run_artifact_shape_inventory.json) is a
read-only inventory generated by
`scripts/research/analysis/models/inspect_observation_action_artifacts.py`.
It scanned the selected matched-policy campaign output and the current MTF
architecture comparison output. It extracted recorded observation shapes,
action schemas, checkpoint path/digest references, and SHA-256 values for the
JSON evidence files; it did not load checkpoints.
The separate [MTF architecture screen summary](mtf_architecture_screen.json)
captures a one-seed, three-variant negative result with hashes for the source
run report and run specification. Its test interval is exposed and its action
contract is distinct from the selected trade-setup comparison.

The run records contain real, run-specific shapes. The MTF run log records
M1 `[60, 160]` plus M3–D1 sequences with widths 71 and their configured window
lengths. The MTF reasoning run records M1 `[60, 322]`, M3–D1 widths 91, and a
`[109]` `thesis_mask` under `thesis-overlay-action-v1`. That is a distinct
historical overlay/action contract, not the configured C/D
`trade_setup_mask` policy contract; the matching width does not establish that
the selected 109-way setup policy used this schema. These are the schemas of
those recorded runs, not a promise that every configured overlay or
checkpoint uses the same tensor widths. The older selected matched-policy artifacts record a single M1
`[60, 746]` stream and a 12-coordinate action schema.

The paired [`Variant C contract`](configured_trade_setup_mtf_contract.json) and
[`Variant D contract`](configured_trade_setup_mtf_conditioned_contract.json)
instantiate both current configs using only the configured training window.
Each records 351,432 train rows, 56,245,046 training ticks, a `[60, 282]` M1
stream, eight HTF streams of width 60 with their exact windows and masks, a
six-coordinate action, and a 109-choice setup mask. Their training data,
source hashes, observation schemas, and action schemas are identical. Variant
D declares a 32-dimensional setup embedding and 128-unit execution head;
source inspection confirms its setup selector still receives only the market
latent. Neither config supplies candidate entry/stop/target/TTL geometry to
the policy. The reports hash each resolved config, 20 local input files, 16
implementation sources, train bars/features, and the bounded tick slice. They
use reset only to verify returned shapes; they take no policy action, step no
environment, load no checkpoint, and report no economics. These are current
configured contracts, not historical trained-model tensors.

The configured `MTFReasoningEncoder` now has a synthetic history-sensitivity
regression: changing an earlier valid M5 row changes its output while the
latest row of every timeframe stays fixed. This proves that the encoder uses
some preceding path information rather than only the latest candles; it does
not show that the information improves decisions or trading outcomes.

`test_trade_setup_conditioned_distribution_masks_and_conditions_execution`
also confirms that perturbing the selected setup ID changes execution-head
outputs while the selector receives the unchanged market latent. The passing
PPO update/checkpoint-roundtrip test verifies stored-action log-probability
agreement and save/load compatibility for that schema. These tests establish
categorical ID conditioning and policy plumbing only; the model has no
candidate-specific proposed entry/stop/target/TTL geometry input.

No qualifying per-decision selected-setup trace or candidate price-geometry
trace was found in the scanned artifacts. Trade-level examples and aggregate
setup counts are intentionally not treated as decision traces. The historical
100k replay note independently says its wrapper did not preserve a per-
decision setup trace. This is a scoped absence finding, not a claim that no
other trace exists outside the scanned roots.

The inventory recognizes the evaluator's canonical
`trade_setup_decisions.csv` export and its `trade_setup_candidate_id` field.
It requires a non-empty trace row, so a header-only export does not count as
observed policy decisions. It requires populated decision and setup identifiers;
for a price-geometry trace, entry, stop, target, and time-to-live must also be
populated together on the same row. The historical selected-campaign scan
found no such file in its roots. A broader
[`decision trace availability inventory`](decision_trace_availability_inventory.json)
then scanned 276 recognized artifacts under `outputs`, `baseline`,
`evidence/research`, and the external agent-plan working directory. It found
recorded observation shapes and action schemas, but no qualifying per-decision
setup or candidate price-geometry trace. This is a scoped absence finding:
the scanner recognizes documented manifest names and explicitly named trace
files, does not infer decisions from trade summaries, and does not prove that
traces are absent outside those roots. Future evaluation bundles using the
shared writer will be classified as setup-decision traces while remaining
distinct from candidate price-geometry traces.

The live `TradingEnv.step()` info record now exposes the action's exact setup
category ID, action-schema version, selected family/timeframe/direction, and
whether that category was eligible in the decision-step mask. This includes
explicit `NO_TRADE` decisions and preserves the chosen ID when an inactive
candidate is rejected. Raw named action coordinates are included in the same
record, allowing a decision ID to be reconciled with later `order_submit`,
`reject`, `open`, and close events. Focused tests cover eligible, inactive, and
no-trade decisions plus delayed order/open/close attribution. This closes a
missing per-step telemetry link for the 109-way categorical contract; it does
not add proposed entry/stop/target/TTL geometry to the policy observation or
prove complete lifecycle coverage in historical run artifacts.

The shared `evaluate_model` rollout persists those per-step fields into its
`trade_setup_decisions` frame and checks that the environment's decoded ID and
eligibility agree with the action and mask seen by the policy. The integration
trace verifies active, no-trade, and deliberately ineligible decisions against
their event-index ranges and rejection decision IDs. This verifies the current
writer path on synthetic inputs; it does not create new configured-market
evaluation evidence.
